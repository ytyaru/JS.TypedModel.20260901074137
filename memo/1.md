# `struct()`: ディープコピーもnewも拡張もできるがプリミティブ値しかセットできない奴

プリミティブ値しかセットできない。その判定タイミングはいつにすべき？

現状の実装では`strunct({v:isT.p.int, x:someFn})`のように型判定以外の関数も自由にスキーマ定義としてセットできる。そのおかげで将来、型判定以外の処理も自由にセットできる。例えば現在の値から変更されていたら`changed`イベントを発行させリアクティブプログラミング的な構造にするといったことも可能だ。

反面、その関数が型判定であると特定できないせいで、プリミティブ値かどうか判定できない。するとディープコピー時にエラーになる。だがそれはスキーマ定義時点でプリミティブ値のみを定義できりょうにすべきだ。後になってからじつはできませんでした、というのでは罠でしかない。

するとスキーマ定義に使えるAPIを限定する案が考えられる。isT, owT系関数だけを許容する。それ以外は使えない。するとリアクティブプログラミング的な拡張ができなくなるなど自由度が一気に失われる。

`struct`は基本的にプリミティブ型のみを許容すべきかもしれない。これはC言語でいう構造体を想定しているから。だがC言語の構造体もポインタ変数を持つことができる。非プリミティブを持つことができる。

問題が複雑化するのはディープコピーだ。プリミティブはディープコピーできるし、そうするものだ。しかし他のオブジェクト型変数値は基本的にポインタ変数だけを複製し、参照先のメモリ実体は複製しないシャローコピーになる。その理由はヒープメモリ量が多いことやその処理に実行時間がかかることが挙げられる。

ディープコピー用APIにstructuredCloneがある。

* https://developer.mozilla.org/ja/docs/Web/API/Window/structuredClone

ディープコピーと言えばプリミティブ値だけでなくオブジェクト変数値も複製することが特徴だ。しかし全てのオブジェクト変数値を複製できる訳ではない。その必要がない関数などはしない。逆に複製対象となるものは限定的である。

その複製アルゴリズムは以下。

* https://developer.mozilla.org/ja/docs/Web/API/Web_Workers_API/Structured_clone_algorithm

つまり複製されるオブジェクト型とそうでないものがある。その区別をつけ真偽値で返却するAPIなどは公開されていない。JSの仕様変更が入るたびに予告なく変更されるだろうし、ブラウザやバージョンごとに対応が違うだろう。

つまりエンドユーザにとって制御不能だ。例えばディープコピーできないものはシャローコピーする、という対処をするために自力実装しようにも、それがstructuredCloneで対応できる型か否かが判定できない。

もし無理やりtry catch構文で判定するならプロパティ一つずつに対してstructuredCloneを実行することになりパフォーマンスが最悪になる。現実的とは思えない。

上記のことからディープコピーが事を複雑化させるボトルネックである。ならば型の集合を作ることも、それを元に複製することも、どれも非現実的と言わざるを得ない。

# 現実的な範囲は？

値の代入時に指定したvalidator関数を実行するオブジェクトを作成する。

これくらいが実現可能な範囲だろう。

名付けるならば`ValidatableObject`か。

あるいは妥当性検証を型だけに絞れば`TypedObject`か。

```
class MyClassEs6 {}
function MyClassEs5 {}
const humanSchema = T.schema({
  id: T.p.int,
  name: T.p.str,
  obj: T.o.obj,
  cls0: T.o.cls,
  cls1: T.o.cls(MyClassEs6),
  cls2: T.o.cls(MyClassEs5),
  cls3: T.o.cls(Uint8Array),
  clsEs6: T.o.cls.es6(MyClassEs6),
  clsEs5: T.o.cls.es5(MyClassEs5),
  clsNative: T.o.cls.native(Uint8Array),
  ins: T.o.ins(MyClass),
  child: {
    prim: T.p,
  }
});
humanSchema.is({id:0, name:'', obj:{}, child:{prim:0}}); // 型判定: 真偽値返却
humanSchema.throw({id:0, name:'', obj:{}, child:{prim:0}}); // 型判定: 例外発生
```

1. 型判定: メモリ解釈方法や所持メソッドなど扱い方を定義する
2. 値判定: 同じ型でもその値を厳選する（int型でも0〜100の整数値に絞る等）

つまりまずは型判定する。次に値判定する。値判定は型判定できている前提だ。つまり型ごとに独自の値判定があるはず。例えばNumber型なら所定の範囲内か否かを示す`within(v, min, max)`のような値判定があるし、String型なら`length(v, min, max, unit=CodeUnit/CodePoint/Grapheme/Word/Sentence)`のような値判定があるだろう。

更に値判定まで終わると次は以下のようなステップがある。

1. 例外発生させる（任意メッセージを表示する）
2. 真偽値判定で条件分岐する
	* デフォルト値を代入させる等の任意処理を実行し継続するか、そのままの値で継続か
	* 偽の場合、UIに所定のメッセージを表示する

例えば型が違う場合、それはもうプログラミングエラーだ。処理を継続してしまうと問題発生箇所が特定しづらくなる。よって例外発生させ即時中断すべきである。という考えもある。

だが中断されると困る場合も有る。値判定においては不正値が代入されることもありうる状況はよくある。特にユーザが自由に入力できるUIを提供しつつ、しかし膨大なデータベースで重複していないことを確認する必要があり、その結果重複しているから別の値を入力するようユーザに促す必要がある場面などだ。かといってシステムが自動で非重複な値を提案した所で、それが正しくなかったり、ユーザが気に入らないなど、何かしらの問題がありえる。つまりシステムとユーザは互いに自分の基準で値を決めたいが、相手の基準に由って阻まれる事がある。両者の間で妥協した値を入力する必要がある。その場合、たった一度の判定式では明快な答えが出せない。何度も挑戦することで、ようやく妥当な値を発見できる。

判定は合格／失格の二値に大別できる。合格の場合は問題ない。しかし失格の場合は更に細分化し、それぞれに対応を実装せねばならない。

* 合格
* 失格
	* 例外発生
	* 代用値返却による強制合格（ユーザに自由な値を代入できる機会はなくなってしまう）
	* 結果返却（どの項目がどんな理由で失格になったか）
		* メッセージ作成（それを自然言語化する。多言語化処理が必要）
	* 結果返却とそれに応じた処理（合否ごとに所定の処理をする）
		* 処理はコールバック関数でセットするが、内容次第ではasyncな関数を呼び出す必要もありそう
